# 简化方案 v1：VPS Claude 通过 SSH 使用本机渲染

日期：2026-10-08
决定人：用户
状态：**取代**此前的 protocol-v1 r5.1、安全边界和 M1/M2 实现路线。旧文档和代码保留在仓库中，暂不使用，也不删除。

## 1. 决定

1. **取消**“本机公网 IP 不得进入 Anthropic”的限制。VPS 上的 Claude 可以正常进行网络诊断；交接材料不再需要脱敏。
2. 地区信息：不再专门设防，但也不主动收集。
3. 不再做：VPS 沙箱、目录交换队列、发布和接收服务、SFTP 投递、隐私过滤和隔离区。
4. 保留：本机不安装、也不登录 Claude；本机侧使用**独立的非管理员账户**；SSH **只在 Tailnet 上开放，只允许密钥登录**。这几条保护的是你的个人文件和机器安全，与 IP 无关。

## 2. 架构

```text
VPS Claude ──ssh/scp（Tailnet，密钥登录）──▶ 本机 Windows 账户 render（非管理员）
                                               ├─ D:\ClaudeRender\projects\<项目>\   场景代码
                                               ├─ D:\ClaudeRender\runs\<任务>\      帧、日志、视频
                                               └─ 无头 Chrome（GPU）+ ffmpeg
◀── scp 取回关键帧、联系表、日志；完整视频按需取回
```

## 3. 本机侧（本机 Codex，需用户授权后执行）

| 步骤 | 内容 |
|---|---|
| L1 | 新建本地**标准用户** `render`（不用 Microsoft 账户，不加入 Administrators）。确认它读不到其他用户的目录（Windows 默认如此，实测一次） |
| L2 | 安装 Windows 可选功能 OpenSSH Server。`sshd_config` 设置：`PasswordAuthentication no`、`PubkeyAuthentication yes`、`AllowUsers render` |
| L3 | Windows 防火墙：SSH 入站规则的远程地址只允许 Tailnet 地址段（`100.64.0.0/10`），并关闭公用网络配置文件上的这条规则。**不要把 22 端口暴露到公网** |
| L4 | 把 VPS 提供的**公钥**放进 `C:\Users\render\.ssh\authorized_keys`，权限只允许 render、SYSTEM 和 Administrators |
| L5 | 默认 shell 设为 PowerShell。在 render 账户下准备好 Chrome 或 Edge、ffmpeg、Python（或 Node），以及 `D:\ClaudeRender` 工作目录（projects、runs、tools） |
| L6 | **首要技术风险，先验证**：通过 SSH 登录后的会话不是交互式桌面会话，无头 Chrome 可能拿不到 GPU，从而回退到软件渲染（SwiftShader）。验证方法：在 SSH 会话里启动无头 Chrome，读取 WebGL 渲染器字符串，同时用 `nvidia-smi` 观察 GPU 占用。如果拿不到 GPU，备选办法是让 render 账户在交互会话中运行一个常驻进程（例如登录时启动的计划任务），SSH 只负责投递任务。 |
| L7 | **长任务不能随 SSH 断开而终止**：Windows 的 OpenSSH 在会话结束时会结束子进程。用计划任务或其他脱离会话的方式启动渲染，并写状态文件供查询。 |

## 4. VPS 侧（Claude）

| 步骤 | 内容 |
|---|---|
| V1 | 生成专用密钥 `~/.ssh/id_ed25519_render`，把**公钥**交给用户转给本机 |
| V2 | `~/.ssh/config` 中加一个 `Host render-local`：使用本机在 Tailnet 中的名称，`User render`，`ServerAliveInterval 30` |
| V3 | 写几个小脚本：推送场景代码、启动渲染、查询状态、取回关键帧和日志。场景页面约定 `renderFrame(i, t)`，其中 `t = i / fps`，逐帧导出，不依赖实时播放 |
| V4 | 跑通循环：改代码 → 渲染关键帧 → 取回查看 → 再改 → 预览 → 正式视频 |

## 5. 验证顺序

1. 在 VPS 上执行 `ssh render-local whoami`，能登录，账户是 render 且不是管理员。
2. 在 SSH 会话里确认 GPU 可用（L6）。
3. 后台渲染在 SSH 断开后仍然继续（L7）。
4. P1：5 秒、150 帧，先关键帧、再预览、最后正式视频。
5. 取回关键帧，在 VPS 上能直接查看。

## 6. 另行处理（与本方案无关）

VPS 的 sshd 目前允许 root 用密码登录，并且对公网开放。建议单独加固：改为只允许密钥登录、禁止 root 登录。修改前先确认密钥登录可用，以免把自己锁在外面。

## 7. 验证结果（2026-10-08，VPS → 本机 render 账户）

| 项目 | 结果 |
|---|---|
| 登录 | `ssh render-local whoami` 返回 `<计算机名>\render`。本机 SSH 主机指纹与在本机上查到的一致，已固定到 known_hosts |
| 执行策略 | 系统禁止运行脚本；调用时加 `-ExecutionPolicy Bypass`，只对当次进程生效，不改系统设置 |
| 输出编码 | 本机输出为 GBK；VPS 端用 `iconv -f GBK` 转换（也可以在脚本开头设置 UTF-8 输出） |
| SSH 会话中的 GPU | SSH 会话运行在 session 0。无头 Chrome 默认（D3D11）时拿不到 WebGL；`--use-angle=vulkan`、`d3d11on12`、`gl` 以及旧版无头模式都能用硬件 GPU，渲染器为 RTX 4060 Ti，没有回退到软件渲染 |
| 真实负载 | Vulkan 后端，1920×1080 重着色器，300 帧用时 813 毫秒（约 369 帧/秒），GPU 占用峰值 89%。**选定 `--use-angle=vulkan`** |
| 探测工具的问题 | `Test-RenderGpu.ps1` 用 `&` 调用 chrome.exe，取不到它的标准输出；需改用 `Start-Process -Wait -RedirectStandardOutput` |
| SSH 断开后继续运行 | **不能**。SSH 会话里用 Start-Process 启动的进程，在断开后约 5 秒内被终止；render 账户没有 WMI 权限；`schtasks /create /np` 会停下来等待输入密码。非管理员账户无法自行实现“断开后继续运行” |

## 8. 第一次完整流程（2026-10-08）

**工具**：
- 本机：`D:\ClaudeRender\tools\claude\`，包括 `render.ps1`、`harness.html`、`harness.js`、`list-runs.ps1`，源码在仓库的 `render/local/` 下。
- VPS：`render/rr`，子命令有 tools、push、render、wait、fetch、runs。
- 场景：`projects/demo/index.js`，约定导出 `setup(ctx)` 和 `renderFrame(i, t)`，其中 `t = i / fps`。

**每次运行**：
- 新建 `D:\ClaudeRender\runs\<项目>-<UTC时间>-<随机4位>\`，从不覆盖已有目录。
- 先把场景代码复制一份快照进去。
- 本机起一个只监听 localhost 的 HTTP 服务，页面逐帧把 PNG POST 回来落盘。
- 渲染期间用 `nvidia-smi` 采样 GPU 占用。
- `run.json` 记录参数、耗时和状态；`SUCCESS` 最后写入，加了 `-Encode` 时在编码完成后才写。

**发现并修正的问题**：
1. 在 session 0 中，Chrome 新版无头模式必须加 `--disable-gpu-compositing`，否则 WebGL 上下文会丢失。WebGL 本身仍然走 Vulkan GPU。
2. 用 `taskkill /T` 结束 Chrome 被拒绝访问；改为 `Process.Kill()` 只结束主进程，Chrome 的子进程会随之退出。
3. `gl.finish()` 不会真正等待 GPU 完成；改用 1 像素的 `readPixels` 强制同步，渲染和导出才能分开计时。
4. 演示场景最初的 `sin` 哈希在 Vulkan 下精度不够，出现三角形碎块和接缝；改为不依赖 sin 的哈希后消失。

**成功运行 `demo-20261008T114828Z-99c9`**（1280×720，30 帧/秒，150 帧）：

| 阶段 | 耗时 |
|---|---|
| 启动 Chrome 到收到第一帧 | 0.88 秒 |
| GPU 渲染（150 帧合计） | 0.23 秒（约 1.5 毫秒/帧） |
| 逐帧导出：PNG 编码、回传、写盘（150 帧合计） | 4.7 秒（约 31 毫秒/帧） |
| 浏览器阶段合计 | 5.9 秒 |
| GPU 占用峰值 | 36%，无软件回退 |
| 编码 | **本机没有 ffmpeg，未执行**。临时在 VPS 上编码：27 秒，H.264，5.0 秒，2.2 MB |
| 帧序列从本机取回 VPS（127 MB） | 326 秒（约 0.4 MB/s，Tailscale 直连） |
| 视频从 VPS 上传回本机（2.2 MB） | 12 秒 |

结论：本机与 VPS 之间的带宽很窄，**不应把整套帧序列传回 VPS**。只取回关键帧和小预览，编码必须在本机完成。

**待办**：在本机安装 ffmpeg 到 `D:\ClaudeRender\tools\ffmpeg\bin\ffmpeg.exe`（便携版即可，需要用户批准）。之后用 `rr render demo -Encode` 在本机完成编码并写入 `SUCCESS`。

临时视频放在 `D:\ClaudeRender\runs\demo-20261008T114828Z-99c9\video.vps-encoded.mp4`。这次运行没有 `SUCCESS` 标记，因为编码不是在本机完成的。早先失败的几次运行目录（3 个 demo、1 个 tri）原样保留。

## 10. SSH 断开的实测与改进（2026-10-08）

**结论更正**：第 7 节写的“SSH 断开后进程会被终止”，只适用于**后台启动的子进程**，而且是在会话的主命令已经结束之后被清理。`render.ps1` 是会话的**前台主命令**，客户端断开后 Windows 的 sshd 不会终止它。实测两次：一次用 SSH 连接复用，一次不复用；都是在第 10–12 秒切断，本机都把 1080p、900 帧的渲染和编码跑完，写入了 `SUCCESS`，也没有残留进程。

**改进**：
- 运行编号由 VPS 生成，经 `-RunId` 传给本机，同时保存在 `<log>.runid`。断线后 VPS 仍能找到对应的运行目录。
- `rr wait`：SSH 没有返回摘要时，改为每 10 秒用 `rr status` 查询本机状态，直到出现终态。实测断线后 79 秒拿到了最终结果。
- 状态判断：`render.ps1` 把进程号写入 `runner.pid`。`list-runs.ps1` 和 `rr runs` 显示 succeeded、failed、running 或 interrupted，不再长期停在 `rendering`。
- 渲染期间调用 `SetThreadExecutionState`，阻止 Windows 进入睡眠。**已验证**：2026-10-08 在一次 3000 帧渲染期间，用户以管理员身份运行 `powercfg /requests`，在 SYSTEM 一栏中看到了渲染进程。调用结果也记录在每次运行的 `run.json` 里（`keep_awake_requested`）。
- `rr render` 使用独立连接，不走连接复用，这条连接的生命周期只属于这次渲染。

**1080p、900 帧（30 秒）的耗时**：GPU 渲染 6.0 秒；逐帧导出 62.4 秒（约 69 毫秒/帧，是主要开销）；编码 15.2 秒；合计 84.4 秒；视频 11.9 MB。

**仍然存在的限制**：本机关机、重启，或者渲染进程本身崩溃，都会使运行中断，这类情况需要人工重跑。这是第一版有意接受的范围。

## 11. 无损提速（2026-10-08）

**要求**：不影响画质。**验证办法**：用 `-VerifyMd5` 让 ffmpeg 输出送进编码器的每一帧像素的 MD5（`logs\input.framemd5`），并比较最终 `video.mp4` 的 SHA-256。

1080p、900 帧（30 秒），编码参数完全相同（libx264，preset slow，crf 18）：

| 方式 | 总耗时 | 输入像素与基准一致 | 视频与基准相同 |
|---|---|---|---|
| A. PNG 串行，先渲染后编码（原方式，作为基准） | 90.3 秒 | 基准 | 基准 |
| B. PNG 并行 4 路，先渲染后编码 | 59.7 秒 | 900/900 | 逐字节相同 |
| C. 原始 RGBA 流式送入 ffmpeg | 92.1 秒（每帧 8 MB 从浏览器 POST 出来太慢） | 900/900 | 逐字节相同 |
| **D. PNG 并行 4 路，按帧序送入 ffmpeg，边渲染边编码（现在的默认）** | **43.6 秒** | 900/900 | 逐字节相同 |
| E. 同 D，并行 8 路 | 41.6 秒 | 900/900 | 逐字节相同 |

**默认设置**：`-Mode png -Inflight 4`。加了 `-Encode` 时边渲染边编码；PNG 照常写盘，可以逐帧检查。stream 模式保留但不推荐。没有采用 NVENC，因为它会改变画质。剩下的主要耗时在浏览器内的 PNG 压缩（约 35 秒）。

## 13. 成品目录与工作区清理（2026-10-09）

- **成品目录**：`D:\ClaudeRender\output\<项目>\<项目>_<yyyy-MM-dd_HHmm>[_<标题>]_<宽>x<高>_<fps>fps_<时长>s.mp4`，以 NTFS 硬链接发布，不额外占用空间；删除运行目录后成品仍然保留。同名附带 `.json`（参数、耗时、sha256、复现命令）和 `.scene.zip`（场景代码快照），`output\index.csv` 每个成品一行。用 `-NoPublish` 可以让测试运行不进入 `output`。
- **自动瘦身**：每次运行结束删除 Chrome 临时配置（约 3.6 MB/次）；`-Encode` 成功后只保留首、中、尾关键帧（`-Keep` 指定，`-KeepFrames` 保留全部）。
- **一轮结束即清理（标准步骤，无需等用户确认）**：成品发布、并用联系表核对过之后，立即运行 `rr prune --project <项目> --apply`，删除这个项目的全部过程运行，不论时间长短（关键帧预览、失败运行、`-NoPublish` 测试）。即使用户不满意，这些运行也没有利用价值：修改意味着重新渲染；看图用的关键帧已取回 VPS；成品、参数和代码快照都在 `output` 里；代码历史保存在 VPS 端。例外只有两种：渲染还在进行，或者失败原因还没查清。
- **兜底清理**：`rr prune [天数] [--apply]` 删除超过指定天数（默认 14 天）的运行，用于处理被遗忘的运行。两种清理都会跳过正在运行的运行、`output` 和 `_` 开头的诊断目录；VPS 端的旧日志一并清理。
- **可复现性实测**：同样的代码和参数重新渲染，视频 SHA-256 与已发布的成品完全一致（`ebda8995…15b3`）。因此清理工作区不会丢失任何成品对应的信息。
- **一次性清理**：删除了全部 43 个测试运行（493 MB）；`output` 从空目录开始；`runs` 只保留 Codex 的诊断目录（12 MB）。
- 这套流程已写进全局 skill `local-gpu-render`（模板在 `docs/claude-skill/SKILL.md`）。
